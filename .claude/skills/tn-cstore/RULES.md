# tn-cstore rules

If `LOCAL.md` exists next to this file, read it too. It holds this vault's own decisions (preferred vocabulary, history) and wins over this file where they differ.

## Layout
- `00_Staging/daily-notes/` and `00_Staging/articles/`: inbox, emptied by processing. Images can sit next to the article in staging (any subfolder) or in `attachments/`.
- `raw/<slug>.md`: full text of a page (markdown). **No backlinks, no tags. Never edit the body.** One exception: if a staged article already contains Obsidian `[[backlinks]]`, unwrap them in `raw/` only (`[[X]]` becomes `X`, `[[A|B]]` becomes `B`) so `check.py` passes. Image embeds (`![[x.png]]`) are not backlinks: leave them as they are. Change nothing else.
- `raw/attachments/`: images that articles in `raw/` embed. Obsidian stores pasted images in `attachments/` at the vault root. `ingest.py article` copies each image an article embeds (`![[x.png]]`, `![[x.png|300]]`, `![](attachments/x.png)`) into `raw/attachments/`, and `ingest.py finish` removes the source copy (a move overall). Embeds keep working because Obsidian finds them by file name. Never put images in `raw/` itself.
- Remote images in fetched pages (`![](https://...)`): `fetch.py` downloads the images of every fetched page into `raw/attachments/` and replaces only the URL in the link (`attachments/<article-stem>-<hash>.<ext>`; an image already stored under the same hash is reused). Images it cannot download (blocked, gone, not an image, over 15 MB, YouTube links) keep their absolute URL. The same applies to staged articles: `ingest.py article` downloads their remote images (`![](https://...)`, relative paths resolved against the `source` URL) into `raw/attachments/` and replaces only the URL in the link. The shared code is `tools/images.py`.
- `raw/<slug>.summary.md`: summary. **Only place with backlinks**: tags in front matter, inline `[[links]]` on first mention, a `Full text:` and `Related:` line.
- `notes/`: flat folder of hub notes (topic, person, entity, concept) plus `_index.md`. Generated by `tools/link.py`. Each hub has `para`, `status`, `area`, `projects`.
- `01_Projects/`, `02_Areas/`: hand-written notes, created once, never overwritten.
- `03_Resources/`: reserved, empty until the user moves files in.
- `04_Archive/daily-notes/`: processed daily notes. Daily notes get no backlinks.
- `04_Archive/pdf/`: source PDFs of processed articles. A staged PDF is converted to `raw/<slug>.md` (front matter `converter: pdf`, source `local:<file name>`), then handled like any article.
- `tools/`: `classification.json` (tags and optional project per article, keyed by file name without `.md`), `descriptions.py` (one line per hub, plus optional `ALIASES`: other spellings that count as a mention), `para.py` (areas, projects, archive, resource groups), `urls.tsv`, `results.json`. `init.py` creates any of them that are missing (a new store starts from `/tn-cstore-init`).

## Linking rules
- Dates are plain text, never `[[links]]`.
- A hub exists for every topic and person, and for entities and concepts that appear in 2 or more articles. Single-use terms stay plain text in front matter.
- Link a person only if the article is about them, not for every name mentioned.
- Canonical names are English. Merge variants ("Dalio", "Ray Dalio's") into one name.
- A person is a person note, never also a topic (Ray Dalio is a person).
- Reuse existing vocabulary first (`python3 tools/ingest.py vocab`; it also lists terms seeded in `descriptions.py` that have no article yet, with count 0). Names the user already uses in the vault take priority over new ones.
- A new store has little vocabulary, so the first articles bring many proposals. Batch them: one AskUserQuestion per article (or per batch of articles) listing all proposed new terms, not one question per term.
- A topic that is in no area and no resource group shows under "Ungrouped topics" in `notes/_index.md`. Offer `/tn-cstore-assign` when that list grows.

## Projects of articles
- An article has at most one project (`project` in `tools/classification.json`, shown as `project: "[[Name]]"` in the summary). The project is a relation, never a location: the file always lives in `raw/`.
- Hint: staged file in `00_Staging/articles/<project name>/` or `project:` in its front matter. A hint is explicit and needs no confirmation.
- No hint: `python3 tools/ingest.py suggest` proposes a project when the article shares 3 or more hubs with it. Always confirm in one batched question. No proposal means no project.
- Each project note has a block between `<!-- cstore:articles -->` and `<!-- /cstore:articles -->`. `link.py` refreshes it; never edit it by hand.

## Ask, do not guess
Use AskUserQuestion when any of these is unclear:
- a new topic, person, entity or concept would be needed
- which area or project a hub belongs to
- the date of a daily note that is not named `YYYY-MM-DD`
- two readings of an article are both plausible
Show the proposal (term, why, existing alternatives) and wait. Never add vocabulary silently.

## Summary style (`raw/*.summary.md` body)
- 3 to 6 sentences, one paragraph. Say what it claims, with numbers and names. State the stance (opinion, news, how-to).
- If the page was partial (paywall, login wall, only a teaser, empty), say so plainly. Never fill the gap.
- Mark unverified claims as opinion. Note when a page is a rolling page that changed since it was saved.
- Plain voice: short sentences, no em dashes, no hype or filler words (leverage, robust, seamless, crucial, delve, and similar), no "not X, but Y" constructions.
- Quote nothing at length. Write the summary from the page, not from memory.

## Safety
- Run `python3 tools/check.py` before every commit. Zero errors required.
- Never delete files in `raw/`. Staged originals are removed only by `ingest.py finish`, which only touches fully processed items.
- Git: `git pull --no-rebase origin main` first (the user edits via Obsidian and pushes too), commit with a clear message, `git push origin main`. If the repo's default branch is not `main`, use that branch in every command. Never force-push, never rewrite history.
- Do not write to `01_Projects/` or `02_Areas/` files that exist. Edit `tools/para.py` for assignments instead. Exception: when the user explicitly chooses a project note as the destination for staged material (for example their own article outline), append it there, link to the summaries of the articles it mentions, and say so.
- Project working folders: `01_Projects/<project>/` holds the user's own files for a project (brand files, site source, drafts, assets), moved there as they are, never summarised, tagged or checked. The project note `01_Projects/<project>.md` sits next to the folder.
- A project hint is the first subfolder under `00_Staging/articles/`. Deeper subfolders do not count.
- Staged files that are not saved articles (own outlines, drafts, notes) are not added to `raw/`. Ask where they go.
